# Obscura Protocol v0.2 (draft)

Memo prefix: `obscura:v0:`. Nothing has shipped yet, so v0 stays until the first mainnet round; after that, bump the version if any format changes. Memos are UTF-8 text, max 512 bytes (ZIP-302).

## Changes from v0.1
- Auction is **first-price** sealed-bid (was second-price). Removes the operator shill-bid attack.
- Vote memo can carry an optional **patron pubkey** for anonymous patron badges.
- New memo type: **whisper** (paid theme suggestion).
- Two wallet accounts (voting, auction) with fresh Orchard-only addresses, instead of one account per round.
- Deterministic tie-breaks down to txid + output index.
- Refund rules for invalid bids; flat refund fee from config.
- Canonical bytes for signatures (RFC 8785).
- Treasury survival states.

## Accounts and addresses

| Account | Receives | Viewing key |
|---|---|---|
| `voting` | votes, whispers, donations | IVK held by detector; may be published per round later (see §7) |
| `auction` | bids | IVK held by detector; **never published** (would reveal bid amounts and refund addresses) |

- Every round gets a fresh **Orchard-only** Unified Address from the `voting` account (`round_ua`, new diversifier index). Every auction gets a fresh Orchard-only UA from the `auction` account (`auction_ua`).
- The detector maps each received note to its round/auction by the receiving address (diversifier index), not by the memo. A memo whose id doesn't match the receiving address is treated as malformed.
- Only Orchard notes count. Funds arriving in any other pool are recorded as rejected donations.

## Timing

- Each round/auction has `open_height` and `close_height` from config (`VOTING_BLOCKS`, `AUCTION_BLOCKS`).
- A payment counts if it was **mined** at a height `h` with `open_height ≤ h ≤ close_height`.
- Tally/clearing runs once the chain tip reaches `close_height + CONFIRMATIONS`.
- Canonical ordering of payments, used for every tie-break: `(mined_height, txid hex ascending, output index ascending)`.

## Round lifecycle

```
OPEN_VOTING ──(close)──> TALLIED ──> AUCTION_OPEN ──(close)──> SETTLING ──> SETTLED
```

All state changes are driven by deterministic code and block heights from config, never by LLM output.

## 1. Voting

Each candidate is shown with a ZIP-321 URI (amount in ZEC decimal, memo base64url without padding):

```
zcash:<round_ua>?amount=<suggested>&memo=<base64url("obscura:v0:v:<round_id>:<candidate_id>")>
```

Vote memo:

```
obscura:v0:v:<round_id>:<candidate_id>[:<patron_pubkey_hex>][:<note>]
```

- `round_id`: e.g. `r0007`. `candidate_id`: `a`..`h`.
- `patron_pubkey_hex` (optional): 64 lowercase hex chars, an Ed25519 public key the patron generated (see §5).
- `note` (optional): free text to the artist. Shown publicly only if it passes the content filter; never parsed for money.
- Parsing: split on `:`. The sixth field is a pubkey only if it is exactly 64 lowercase hex chars; otherwise everything from the sixth field on is the note (notes may contain `:`).

Rules:
- Weight = note value in zatoshis. Counted only if `value ≥ MIN_VOTE_ZAT`. Smaller payments are donations.
- **Weight is linear on purpose.** Shielded payments can be split into any number of notes from any number of addresses, so quadratic or per-person voting can't be enforced. One zatoshi = one unit of weight is the only honest rule.
- Late votes (mined after `close_height`) aren't counted; they stay in the treasury and are listed as "late".
- Malformed memo or unknown candidate → donation.
- Ties: the candidate whose first counted vote comes earliest in canonical order wins.

## 2. Whispers (paid theme suggestions)

Sent to the current `round_ua`:

```
obscura:v0:w:<round_id>:<text>
```

- Counted if `value ≥ MIN_WHISPER_ZAT` and mined during the round. Otherwise donation.
- Whispers that pass the content filter are given to the agent at the next Reflect step, ranked by amount (ties by canonical order). The agent may use or ignore them and says so in its journal.
- Whispers never affect money, tallies or auction rules.

## 3. Sealed-bid auction (first-price)

Bid = shielded payment of the **full bid amount** to `auction_ua`. Memo:

```
obscura:v0:b:<auction_id>:<claim_pubkey_hex>:<refund_ua>
```

- `claim_pubkey_hex`: Ed25519 public key generated by the bidder for this auction (64 hex).
- `refund_ua`: Unified Address with an Orchard receiver.

Classification:
- **Valid bid:** well-formed memo, matching `auction_id`, mined in the window, `value ≥ reserve_zat`.
- **Refundable invalid bid:** not valid, but the memo has a parseable `refund_ua` with an Orchard receiver (e.g. late, below reserve, wrong auction id).
- **Unrefundable:** no usable `refund_ua` → donation.

Clearing:
- Winner = highest valid value; ties broken by canonical order.
- **Price = winner's bid.** The winner gets no refund.
- Every other valid bid and every refundable invalid bid is refunded `value − REFUND_FEE_ZAT`, sent to its `refund_ua` with memo `obscura:v0:refund:<auction_id>:<reason>`. If `value ≤ REFUND_FEE_ZAT`, no refund is sent (donation).
- Refunds are sent in batches of at most `REFUND_BATCH_SIZE` outputs per transaction, keyed by the bid's `(txid, output_index)` so each bid is refunded at most once.
- Published: clearing price and number of valid bids. Individual losing bid amounts are never published.
- No valid bids → piece stays in the artist's collection; may be re-auctioned later. Refundable bids are still refunded.

Why first-price: the operator can see bids live through the IVK. In a second-price auction it could add a fake bid just under the top bid to raise the price the winner pays. In first-price, the winner pays their own bid, so a fake bid can't change it.

## 4. Claim

1. Server issues a challenge: `obscura:v0:claim:<auction_id>:<nonce>` (nonce: 16 random bytes, hex, single use, expires).
2. Winner signs the challenge's UTF-8 bytes with the claim key; server verifies against the winning bid's `claim_pubkey_hex`.
3. Server returns the full-resolution file and a **provenance certificate**:

```json
{ "type": "obscura.provenance.v0", "piece_id": "...", "round_id": "...", "auction_id": "...",
  "price_zat": 0, "claim_pubkey": "...", "image_sha256": "...", "artist_sig": "<Ed25519 by artist key>" }
```

**Shielded collectible: not available.** The spike checked whether a Zcash shielded asset standard could carry the piece as a token. ZSAs (ZIPs 226/227) are still Draft and not part of NU7 (docs/SPIKE.md), so the signed certificate above is the ownership record. If ZSAs activate later, a one-of-one token bound to `image_sha256` can be added without changing anything else here.

## 5. Patron badges

A patron who put `patron_pubkey_hex` in a counted vote can prove it later without revealing identity or amount.

- After tally, the server publishes a **badge registry** per round: for each candidate, the list of patron pubkeys from counted votes (no amounts, no notes).
- To get a badge, the patron signs the challenge `obscura:v0:badge:<round_id>:<nonce>` with their patron key. The server returns a badge certificate signed by the artist:

```json
{ "type": "obscura.badge.v0", "round_id": "...", "candidate_id": "...", "won": true,
  "patron_pubkey": "...", "artist_sig": "..." }
```

- Anyone can verify the badge with the artist's public key, and cross-check the pubkey against the public registry.
- A badge shows which candidate the patron backed and whether it won, nothing else.

## 6. Signatures

- All Ed25519 (`@noble/ed25519`).
- Certificates are signed over the **RFC 8785 (JCS) canonical JSON** of the object without the `artist_sig` field. Fields are strings and integers only, so JCS reduces to: keys sorted, no whitespace, standard string escaping.
- Challenges are signed as their UTF-8 bytes. Every signed string starts with `obscura:v0:` plus a type tag, so a signature for one purpose can't be replayed for another.

## 7. Treasury and survival

- Treasury = spendable Orchard balance across both accounts minus bids still held for refund.
- `runway_days = treasury_zat / DAILY_SPEND_ZAT`.
- Survival state, given to the agent at every Reflect step and shown on the site:

| State | Runway |
|---|---|
| thriving | > 30 days |
| steady | 7–30 days |
| struggling | 1–7 days |
| dormant | < cost of one round |

- In `dormant`, the artist makes no new pieces. It keeps writing journal entries and resumes when patrons fund it.
- Within config bounds only, the agent picks pieces per round (`PIECES_MIN..PIECES_MAX`) and reserve (`RESERVE_MIN_ZAT..RESERVE_MAX_ZAT`). Code clamps every value.

## 8. Auditability (should ship)

Move voting to one ZIP-32 account per round and publish that account's IVK after the round closes, so anyone can recompute the tally. This reveals that round's vote amounts and memos (including notes and patron pubkeys), never senders. Auction IVKs are never published.

## Trust model

- The operator (holding IVKs) sees votes, whispers and bids live. Tallies are public anyway; bid amounts are not.
- First-price clearing means the operator can't raise the winner's price with a fake bid. It could fake-win its own auction, which only keeps the piece unsold.
- Refunds depend on the operator's hot wallet. Keep it small; roadmap: FROST multi-sig treasury.
- The AI agent cannot move funds; all payouts are deterministic.
